Two models, one process

        
Couple an upstream model to a downstream model

        

        
After every 5-second routing step, the flow arriving at the upstream outfall OA is set as lateral inflow at downstream node IN. The check is the same network built as one model, where the upstream pipe drops 5 ft into IN.

        

      

      
Read the difference honestly. One-way coupling passes nothing back upstream, and a free outfall is not a drop structure, so coupled and merged should be close, not equal. What must be exact is the bookkeeping: both clocks advance together and every handle stays independent.

About swmm5-cplus

        
swmm5-cplus is EPA SWMM 5.2.4 restructured as C++17 so that each simulation is an object. Nothing it computes differs from EPA's engine; what changes is that a program can hold, step and couple any number of models at once, in one process, a thread each, or one WebAssembly instance.

        
The EPA Storm Water Management Model is a work of the U.S. Environmental Protection Agency, in the public domain. Version 5.2.4's engine is Lewis Rossman's design; swmm5-cplus keeps every algorithm as he wrote it.

AI use

        
swmm5-cplus, this app and its Doc essay were built with Claude, Anthropic's AI model (Claude Opus 5.5), in one session on 27 and 28 October 2026, at the request of Robert (Bob) Dickinson, who asked the question and supplies the model corpus it was tested on. Responsibility for publishing the work is his.

        
What Claude did: ran the libclang census of EPA's source; wrote the generators that made the C++ tree (make_cplus.py, transpose_xsect.py) and every hand-written change after them; found and fixed the resource defects; wrote the handle and C++ APIs, the coupling example, the WebAssembly builds, the in-memory file system they run on here, the gate and timing harnesses, this page, its figures and the essay. Later on 28 October it profiled the engine, ran the compiler, threading, routing-option and arithmetic experiments in the essay's speed section, and wrote the outfall memo that became R4. That evening two Claude sessions worked on SWMM6 side by side. One read its source, wrote tools/loc_buckets.py to count the three engines and wrote the Doc tab's section on the other C++ SWMM. The other, with Bob's go-ahead to build and run SWMM6's code, built SWMM6's new and legacy engines, ran the four-engine gate, the timing, the callgrind profile and the attribution patches, and wrote the sections from Records against columns onward. SWMM6 itself is the work of Caleb Buahin and the OpenSWMM team; nothing of it is redistributed in this page.

        
How it was checked: mechanically, not by the AI's judgment. Byte comparison of every .out and .rpt against EPA 5.2.4 built from the official tag; AddressSanitizer; interleaved timing with a noise floor. Not yet checked by a person: the generated C++ and the hand edits have not been reviewed line by line by Bob, and the gate has not been rerun on his machine.

Same numbers, different bones

    
EPA SWMM 5.2.4 can hold one model per program. swmm5-cplus is the same engine rebuilt in C++ so each model is an object: every output matches EPA's byte for byte, and a program can run as many models as it likes.
